# Web build (MU Moldova)

MuMain compiled to WebAssembly, playable in desktop Chrome or Edge: Emscripten with JSPI (the
game's blocking main loop suspends to hand the browser a turn), SDL3's experimental WebGPU GPU
backend, the game data on the web server, and the game protocol over WebSockets. MU Moldova runs it
at https://skynet-mu.net/play/ since 2026-10-23.

In the MU Moldova repository: `scripts/build-web.sh` builds it into `out/build/web/src`, and
`scripts/serve-web.py` (which runs `server/web/serve-web.py`) serves that folder with the headers it
needs and bridges WebSockets to the local OpenMU; open http://localhost:8090/.
`scripts/publish-web.py` uploads a build to the VPS, where the same `serve-web.py` runs in a
container behind Caddy (`server/README.md`, "Browser client").

## Toolchain

- **emsdk 6.0.13** (`EMSDK_DIR`, default `F:/trench/toolchain/emsdk`).
- **SDL with the WebGPU backend**: https://github.com/TheeStickmahn/SDL_wgpu at commit
  `09026288bffe2bf9d7451255b766256a34bd8963` (libsdl-org/SDL#16020) plus `patches/sdl-webgpu.patch`
  (`git apply` in the checkout). `MU_SDL_SOURCE_DIR` points CMake at it; the web build requires it.
- **naga-wasm 30.2.0** (npm) for the shader conversion below. Only needed after shader changes.

## How the pieces fit

| Piece | Where | What it does |
| --- | --- | --- |
| Page | `src/web/index.html` | Checks WebGPU, JSPI and cross-origin isolation; downloads `startup.pack` while the code loads; log panel. `?profile` samples the page's code (`muProfileTop()` in the console), `?heartbeat` logs whether the browser gets idle time, `?packets` logs every packet sent and received, unencrypted (`WebNetwork.cpp`). |
| Files | `Core/Platform/web/WebFileSystem.*` | `/game` in memory: the startup pack's files, links to a WasmFS fetch mount (`/server`) for the rest, which download on first read, and writable copies of `config.ini` and friends. |
| Startup pack | `tools/web/make_startup_pack.py`, `src/web/startup-files.txt` | The ~3,800 files the game reads up to character selection, in one download (164 MB) instead of thousands of requests. Regenerate the list from a run of `serve-web.py --access-log`. |
| File list | `cmake/WriteWebFileList.cmake` | `files.txt`, every file the browser may read. |
| Network | `Core/Platform/web/WebNetwork.*`, `WebPacketWriting.h` | The C# ClientLibrary's exports in C++: WebSocket connections to `ws/<port>` beside the page (`/play/ws/<port>` for a page at `/play/`), the hand-written sends, and the `Send<Packet>` functions generated by `tools/web/gen_web_packets.py` from OpenMU's packet XML (checked against `source/Dotnet/PacketBindings_*.h`). `PlatformLibrary.cpp` hands them out for "MUnique.Client.Library". |
| Encryption | `Core/Platform/web/MuPacketCrypto.*` | Xor32 and SimpleModulus as OpenMU's network library does them; `crypto-test/` checks it byte for byte. |
| Packet test | `tools/web/packet-test/` | Checks every generated `Send<Packet>` byte for byte against the desktop library's (`run.sh`, about 15 s; see its README). |
| Shaders | `src/shaders/compiled/*.wgsl`, `Core/Platform/web/RmlUiShadersWgsl.h` | WGSL from the SPIR-V blobs (see below). |
| RmlUi shaders | `Core/Platform/web/RmlUiGpuShaders.cpp` | RmlUi's SDL_GPU renderer asks for SPIR-V; the build redirects its two calls here, which hand out the WGSL version by the SPIR-V's hash. |
| Desktop-only libraries | `Core/Platform/web/include`, `TurboJpegShim.cpp`, `CurlFileDownloaderWeb.cpp`, `PlatformCryptoWeb.cpp` | libjpeg-turbo through SDL_image; no downloads and no saved passwords in the browser. |
| Resolution | `index.html` `muDisplay`, `Core/Platform/web/WebDisplay.*`, `Winmain.cpp` `MuWebFollowPageSize`, `MuWebDisplayResolutions` | Options has "Auto" first, the default: the game takes the game area's size in the screen's real pixels (devicePixelRatio), so the picture is drawn 1:1, and draws its interface that many times larger (the content scale, as on a desktop display at 125 or 150 %). It follows window resizes, Fullscreen and browser zoom. The footer's Quality caps the pixels: High 2560x1440 (phones 1.5 million), Medium 1920x1080 (0.75 M), Low 1280x720 (0.4 M); never below 640x480. `?q=high\|medium\|low` sets it, `?dpr=N` stands in for the screen's ratio, `?reset` forgets both. A size picked in Options (the usual sizes up to the screen's pixels, plus the one that fills the window exactly) turns "Auto" off and is scaled to the window, keeping its shape; the browser keeps the choice (`mu-web/resolution`, `mu-web/quality`). |
| Settings | `index.html` `saveConfig`, `WebFileSystem.cpp` `MuWeb_MergeSavedConfig` | config.ini (resolution, volume, …) is kept in the browser's storage (`mu-web/config.ini`) and comes back on the next visit, with the server copy's `[CONNECTION SETTINGS]`. |
| Frame pacing | `Winmain.cpp` `WaitForBrowserFrame`, `SceneCore.cpp` `WaitForNextActivity` | After each frame the game hands the browser a turn and keeps to about 60 frames a second (no cap while loading). `sleep_for` and `yield` would spin without letting the browser deliver network messages. |

## Shaders

The renderer's SPIR-V blobs become WGSL with naga; the SDL WebGPU backend's binding layout differs
from SDL's SPIR-V one, so `wgsl-convert.mjs` renumbers the bindings first and drops naga's Y flip.

```bash
node tools/web/spirv-to-wgsl.mjs <naga-wasm folder> src/shaders/compiled src/shaders/compiled/*.spv
node tools/web/rmlui-shaders-to-wgsl.mjs <naga-wasm folder>   # writes RmlUiShadersWgsl.h
```

RmlUi's blur shaders use array varyings naga rejects; `rmlui-wgsl/` holds hand-written versions.

Soft clip: the world shaders cut off what is nearer than one unit with a clip distance, a WebGPU
feature ARM Mali phones (the Pixel 9) don't have. `spirv-to-wgsl.mjs` also writes a `*_softclip`
copy of the three vertex shaders that write it and of the three fragment shaders paired with them
(`wgsl-soft-clip.mjs`): the vertex shader hands the clip value on as a varying and the fragment shader
drops the pixel where it's below zero. The page tells the game whether the card has the feature
(`Module.muClipDistances`), and the renderer loads the copies without it (`SoftClipShaders.*`,
the log says "clip distances: no, soft clip shaders"). `index.html?softclip` takes them on any card.
To rewrite only the copies from the checked-in WGSL:

```bash
node tools/web/wgsl-soft-clip.mjs src/shaders/compiled
```

## The SDL patch

`patches/sdl-webgpu.patch` (MU Moldova changes to the fork; each is commented in place):

- Prefer the canvas's own format (RGBA8) for the swapchain, so pipelines and passes agree.
- `WEBGPU_Cancel` implemented (it asserted).
- Frames draw into a backbuffer that Submit copies into the canvas: a canvas texture is only valid
  until the page yields, and the game yields mid-frame.
- Texture uploads honour `pixels_per_row`/`rows_per_layer`: the game pads rows to 256 bytes, and
  textures whose width isn't a multiple of 64 (most of the interface) came out scrambled.
- GPU waits yield through a `MessageChannel` message instead of a timer, which browsers stretch to
  4 ms or more: texture loading went from 18 s to 1.4 s. After 100 ms a wait falls back to timers.
- A window without area (a hidden page laid out at 0x0) skips frames instead of creating 0x0
  textures, and `WaitAndAcquireSwapchainTexture` no longer waits forever for one.
- A key event claims keyboard focus when SDL lost it, or typed text was dropped.
- Fences (Enhanced graphics crashed or froze the tab, 2026-10-22; found with AddressSanitizer, see below):
  - `SubmitAndAcquireFence` read the queue from the command buffer that Submit had just freed.
  - `GenerateMipmaps` freed its temporary texture while the command buffer still tracked it.
  - The work-done callback wrote through the fence pointer it kept, after the fence could be freed. It does nothing now: `QueryFence` takes the state from WaitAny's `completed` flag.
  - A frame's fence is registered after its submit, so it can't signal early.
  - `WaitForGPUIdle` uses a fence of its own instead of one re-registered on every submit, which left registrations pending forever.
  - Waiting for several fences counts each one once.

The game itself builds all mip chains on the CPU in the browser (`GlobalBitmapLoad.cpp` `PlanMipLevels`). With the GPU path the heap still got corrupted where AddressSanitizer couldn't see it; Emscripten's WebGPU port isn't instrumented.

To check memory safety, build a second tree with AddressSanitizer: `-fsanitize=address` in the C, C++ and linker flags, plus `-sINITIAL_MEMORY=1GB` for the linker, in its own build folder. Then serve it with `serve-web.py --root <its src folder> --port 8091`. It runs many times slower, but reports the first bad access with the stacks of the allocation and the free.

## Gameplay checked in Chrome (2026-10-22)

Against the throwaway server, two tabs at once (test2 and test3, characters made GMs for `/teleport`):
login, character selection, walking, warps through the M window (Lorencia → Noria, the new map's files load in a few
seconds), combat and kills with experience, the wizard's Energy Ball, MU Helper (Home; settings on Z), zen and item drops,
an NPC shop (Potion Girl Amy: buying an apple took 20 zen and grew the stack), public chat in English and Russian,
whispers between the tabs, sound (the audio context runs after the first click; the login music measured RMS 0.07).
Then, with the server add-on loaded: MU Helper picking up zen and an item (each pickup answered, the item in its
inventory slot), a party (`/party` with the other player one tile away, accepted in the other tab, both party lists
shown), and moving an item in the inventory (the server confirmed the move).
On 2026-10-23, rebased onto the deploy 11 client (`mu-moldova` fbbd471) and against the live add-on and rules: the
character window's advanced stats tab, the jewel bank (deposit of 8 Jewels of Bless), and MU Helper combat with pickups.

Driving the game from a script has limits that real players don't hit:
- The game reads keys once per frame, so a key pressed and released within one frame is missed: hold keys ~150 ms.
- Synthetic `mousemove`/`pointermove` events don't move the game's cursor (Chrome DevTools-protocol mouse events, as the
  Claude in Chrome extension sends them, do), so hovering and selecting players or NPCs needs real mouse events.
- A synthetic `pointerdown`/`pointerup` pair walks the character but doesn't reach the inventory: picking up and
  placing items needs DevTools-protocol clicks.
- The extension types non-Latin text in a way that doesn't reach SDL; `keypress` events with a `charCode` do.
- The throwaway server needs the MU Moldova add-on: `season3.sql` switches off OpenMU's pickup, NPC dialog and buff
  handlers that the add-on replaces. Without it the client sends pickups and nothing answers.

## When the game fails in the browser

`index.html` catches a WebAssembly error, shows "The game stopped" with Reload and "Reset settings and reload", and stops calling into the game. A failure can leave a lock taken, and the next call from the page (saving settings, a key, a network message) would wait for it forever and freeze the tab. `?reset` clears the settings saved in the browser.

The game also sets `SDL_PROP_GPU_DEVICE_CREATE_WEBGPU_PSEUDOMAP_BUFFERS_SMALLER_THAN_N_MB` to 256 MB
(the backend reads it in bytes), so its 64 MB vertex stream is written through the queue instead of
mapped, which waited for the GPU every frame.

## Running from a folder (https://skynet-mu.net/play/)

The page works from any folder: its files, the startup pack and the bridge (`ws/<port>`) are all
found beside the page. Emscripten's fetch backend resolves a relative base against the site's root,
so `WebFileSystem.cpp` gives it the page's folder as an absolute URL; with "." a page at `/play/`
fetched `/Data/...`.

Chrome may keep a page the player left frozen in its back/forward cache, sockets open, and the
browser still answers WebSocket pings for it: the character stayed "already connected". The page
closes its sockets on `pagehide` and reloads if Chrome brings it back. MU Moldova's server side
(`server/web/serve-web.py`) pings every 20 s and drops a connection after a minute without an
answer (a lost network); OpenMU itself drops a client that stops sending its heartbeat.

## Known gaps

- Every browser player reaches OpenMU from the bridge's address, so per-address limits and bans
  apply to all of them at once.
- The friend list's chat windows connect to the chat server's port 55980 (hard-coded in
  `UI/Social/SocialWindowManager.cpp`), which MU Moldova's bridge doesn't relay; they don't open in
  the browser. Whispers and the normal chat use the game server and work.
- Phones: iOS browsers all use WebKit, which has no JSPI, so iPhones can't run it. Android Chrome
  has what the game needs but was never tried; it has no touch controls (right-click, hotkeys) and
  the interface is drawn for 1024x768.
- Files outside the startup pack (other maps, monsters) still download one by one when first read.
- Saved passwords and the in-game downloader are off in the browser.
- A synthetic click (down and up in the same frame) doesn't walk; a real mouse press does.
